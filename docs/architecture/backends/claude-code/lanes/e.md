# Lane E · Asks (D80–D89)

The ask desk: `packages/bridge/src/backends/claude-code/ui/`, tests in `src/__tests__/claude-code/asks/`. Citations: `d.ts:N` = `sdk.d.ts`, `mjs:` = `sdk.mjs` symbol, `T/` = `src/__tests__/claude-code/`.

## Decisions

**D80. One ask per CLI request id; an answered one is replayed, never asked twice.** `AskBook` keeps `requestId → pending promise` and, for the last 32 answered, `requestId → the answer given`. A redelivery while pending gets the same promise and no new interaction; one after the human answered gets the same answer again (the transport-gap case, `d.ts:3076` "callbacks should be idempotent per request_id"); one after a withdrawal is a new ask. The SDK already skips a duplicate of an in-flight id before it reaches the callback (`mjs` `handleControlRequest`: "Duplicate delivery of in-flight request"), so the replay is what matters. Tests: `lifecycle.test.ts` (redelivered request id).

**D81. Permission options** (`permission-options.ts`). `allow_once` first (allow/once/!stopsRun/message none), then `allow_session` (every suggestion with destination `session` or `cliArg`), then one `allow_always_{user,project,local}` per settings destination that has suggestions (scope `always`, `rule` = the CLI's own rule text such as `Bash(npm test:*)`), then `deny_once` (message `optional`) and `deny_stop` (stopsRun, `interrupt: true`). Each option's `PermissionUpdate[]` stays in the desk by option id and is sent back whole as `updatedPermissions`, so a rule is never invented. A suggestion with a destination the desk does not know is never offered. `suppressAlwaysAllowRule` hides the `always` options only (the doc says "persistent"); `defaultToNo` sets `defaultOptionId: deny_once`; `requiresUserInteraction` sets `deliberate`. Allow echoes the original input (`inputEditable: false`); a deny carries the person's words, else "The user denied this request."; `decisionClassification: "user_permanent"` only for a persistent grant (the CLI infers the rest). Lock-screen shape proven with `permissionVerdicts` (`permission.test.ts`).

**D82. A request the contract cannot hold still goes to a human.** PLAN D13 says a nested schema "is declined with a notice"; read as: *the person* declines it. Such a request is raised as a `confirm` whose body says what could not be shown and quotes the server's message; **confirm = decline** (`{action:"decline"}`; for a tool ask a denial), **`confirmed:false` or cancel = dismiss** (`{action:"cancel"}`). Never answered by the bridge. What counts as unrenderable: a property that is not string/enum/number/integer/boolean/array-of-enum (nested object, array of objects, `$ref`, a type list), a `required` name no property defines, an empty `enum`, a schema that is not an object, a URL elicitation whose link is not `http(s)` (never offered to open), `AskUserQuestion` input with repeated question texts or option labels, no questions, or not the documented shape (the CLI itself refuses repeated texts: "Question texts must be unique" in the binary, so that case is defence). `isValidAsk` runs the contract's `Interaction` schema over everything built, so an oversized or odd value degrades to the unrenderable/minimal ask instead of reaching the core.

**D83. Field order is the schema's own key order.** The brief asks to respect `property_order`; the SDK's `onElicitation` receives `{serverName, message, mode, url, elicitationId, requestedSchema, title, displayName, description}` and nothing else (`mjs` `processControlRequest` elicitation branch; `property_order` appears only on the wire type, `d.ts:4018-4042`). `Object.keys` of the parsed schema is therefore all there is (integer-like keys come first, which is the case `property_order` exists for, and cannot be recovered). A `__proto__` property gets another key (`_proto_`, then `_proto__` …, no property uses it) and its answer goes back under the server's own name as an own key (`Object.fromEntries`); proven in unit tests. **Real CLI 2.1.316 never delivers either case**: it refuses a nested schema to the server before the callback (`-32602 Invalid elicitation request`, `real_elicitation.test.ts`), and drops a `__proto__` property from `properties` but keeps it in `required` (the callback sees `{properties:{}, required:["__proto__"]}`, which D82 raises as a decline-or-dismiss confirm).

**D84. Plan approval** (`plan.ts`). Plan from `input.plan`, path from `input.planFilePath`, `editable` when the plan text fits. `modeOptions` from `host.planModeOptions()`, with `defaultValue: "default"` set when the host offers that value and named none. Approve = allow with `updatedInput` the original input, plus `plan` only when the reply's plan differs from the original; the mode is `reply.modeAfter ?? modeOptions.defaultValue` as `updatedPermissions: [{type:"setMode", mode, destination:"session"}]`, refused `invalid_input` when it is not a `PermissionMode`; a host that offers no modes sends no `setMode`. Reject = deny with the feedback (default text "The user wants the plan revised before any work starts."), no interrupt: the session stays in plan mode. Real CLI: `real_plan.test.ts`.

**D85. URL elicitations and the server's completion.** `external_url` accept = `{action:"accept"}` (consent to open the link); cancel = `{action:"cancel"}`. `desk.elicitationComplete(id)` on a pending ask resolves it `withdrawn` and tells the server `cancel` (the bridge claims no consent); on an answered one it does nothing. The CLI's own `control_cancel_request` may also end it: both paths are idempotent (`real_elicitation.test.ts`, `ask_url_early`).

**D86. Failure handling** (D14). `AskFloor.raise` registers an ask in the ledger *before* it emits, and an emit that throws is caught and reported: the state already holds the interaction, so it stays raised and answerable. `interaction_resolved` emit failures never stop the callback from being settled. A builder that throws or builds something the contract refuses degrades to `minimalPermissionAsk` (allow once / deny once / deny and stop, no input shown, `deliberate`). A preview or title helper (lane B's) that fails costs only the preview or the title. If the ask cannot be raised at all (`host.now()` throws), the callback is **parked**: pending until the CLI's signal aborts, answering nothing, so the tool stays blocked rather than denied (`real_failure.test.ts`: no "Tool permission request failed", tool not run). Nothing returns `null`; problems are written to stderr as `[claude-code asks] <where>: <error>` because the adapter's layer allows no logger.

**D87. Text from the CLI or an MCP server is stripped** of ANSI escapes, control characters and bidi overrides (U+200E/F, U+202A–E, U+2066–9) before it is shown (`text.ts`): `decisionReason` "may carry ANSI escapes; sanitize before rendering" (`d.ts:5046`), `mcpServer.name` is "untrusted text, escape it before display" (`d.ts:256-259`), tool names and server names come from config. An elicitation's `title` is the interaction title, its `description` (the permission-display subtitle) leads the body, then `message`.

**D88. `requiresUserInteraction` is not in `CanUseTool`'s declared options** but the runtime passes it (`mjs` `processControlRequest`: `...typeof e.request.requires_user_interaction==="boolean"&&{requiresUserInteraction:…}`; wire `d.ts:5086-5088`; `T/spike/permissions.test.ts:130`). It is read with an `in` check, no cast.

**D89. Stopping the run.** A cancel with `stopRun: true`, or the `deny_stop` option, is answered as a denial with `interrupt: true` *and* the desk asks the host to `abortRun()` (failures reported, never thrown). Order: the interaction is resolved (`answered`), the callback settled, then the abort. `interrupt: true` alone ends the turn (`terminal_reason: aborted_*`, `real_tools.test.ts` with a no-op `abortRun`); the host abort is what makes the run's outcome `aborted` on lane D's side.

## Port changes needed

None. Notes on the ports as they are:

- `AskHost` has no logger; the desk writes to stderr (D86). If the plan owner wants the bridge logger, the factory would hand the desk a `report(where, error)` function.
- `AskHost.activeRunId()` must be defined by the time an ask arrives: the CLI's `control_request` can follow its `assistant` frame in the same chunk. The real-CLI tests have `run_started` emitted at prompt dispatch (D7), which is early enough; an ask raised with no run is `blocksRun: false`, so a run that starts from a frame lane D has not consumed yet would not be blocked.

## What other lanes must do

- **D** (`live/`): call `desk.withdrawRun(runId)` *before* emitting `run_finished` (stream rule: "interactions of the run still pending"); `desk.elicitationComplete(frame.elicitation_id)` on `system/elicitation_complete`; `desk.expireAll()` at process end; wire `canUseTool` and `onElicitation` into every `query()`, never `permissionPrompts: "none"`. `planModeOptions()` should list the catalogue's modes; the desk sets `defaultValue: "default"` if absent.
- **B**: the desk calls `toolTitle(toolName, input)` and `fileChangesOf(toolName, input, undefined)` on a **pending** call (no result yet); both must work on an input alone. CLI 2.1.316 sends no `title` for `Bash` or `WebFetch` asks, so `toolTitle` is the ask's title there (the fallback is `Allow <tool>?`).
- **Integration**: `real_*.test.ts` and `rule23_real.test.ts` run the desk wired into the real CLI through a minimal host of their own (`rig/ask-backend.ts`, `rig/real-cli.ts`); with lane D merged, the conformance suite's rule 23 is the same check over the real host.
