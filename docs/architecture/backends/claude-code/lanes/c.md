# Lane C · Catalogue: decisions D60–D66, facts and hand-offs

> Merged in Step 5 (`cc/integrate`). This file is the lane's record as delivered; where the adapter [README](../README.md)'s integration decisions D120–D129 changed something here, the README wins.

Owns `models/*`, `modes.ts`, `commands.ts`, `status.ts`, `process/probe.ts`, `process/version-check.ts`; tests in `T/catalogue/`. Citations as in STEP-3 (`d.ts:N` = `sdk.d.ts`; `T` = `packages/bridge/src/__tests__/claude-code/`). No port change is needed.

## Decisions

**D60. Models.** `ModelSummary.id` is `ModelInfo.value` (`d.ts:1446`); `isDefault` is the row `default`; `thinking.options` are `supportedEffortLevels` as given, deduplicated, labelled (`Low … Extra high … Max`), no `defaultValue` (the CLI names none); `supportsEffort: false` gives no options. `includeUnavailable` lists the same as the plain list: the CLI's answer carries `unavailable_models` on the wire (binary, `Kk()`), but `SDKControlInitializeResponse` (`d.ts:4783-4837`) does not type it, and reading an untyped field is the cast the rules forbid.
*Order (STEP-3 §11).* `T/conformance/model-echo.ts` maps a request's wire id back to a listed id only when exactly one row resolves to it, else it echoes the wire id; `default` and `opus` both resolve to `claude-opus-5-5`, so neither can be one of the first two listed models. `listedRows` therefore lists rows whose wire id (`resolvedModel ?? value`) no other row shares first, then the sharing rows, each group in the CLI's order: `fable, sonnet, haiku, default, opus` today, and the CLI's own order whenever every row has a wire id of its own. Evidence: `T/catalogue/conformance_catalogue.test.ts` runs the unmodified `ModelEcho` against the real list; mutating the partition away fails it and two other tests. *Product cost:* the phone shows "Default (recommended)" fourth. The alternative is to keep the CLI's order and teach `model-echo.ts` to fold rows that share a wire id (a three-line change to a frozen test helper); the plan owner decides.
*`listedModelId(cwd, wire)`:* an exact `value` match, else the first listed row with `resolvedModel === wire`; a wire id several rows share goes to `default`, so lane D should keep the id it asked for when it has one and use this only for a model the CLI chose. Undefined for a retired id (the CLI remaps it silently, Q11).

**D61. Commands.** One row per name, the row `/name` runs (the `builtin`-marked one, `d.ts:9799`, else the first); commands a user, project, plugin or MCP server defined come before the CLI's own, each group in the CLI's order, so a project command is the first listed one (rule 13); `terminal_slash_commands` are never listed. `initialize` carries no such tag and the `init` frame (which has it) comes only with a turn, so `TERMINAL_BUILTINS` (`color doctor exit focus reload-plugins send-to-project statusline`, every command the 2.1.316 binary tags `terminalOriented`) is fixed, applied only to `builtin` rows, and held to a real turn's `init.terminal_slash_commands` by `T/catalogue/real_catalogue.test.ts` (a pin bump re-runs it). `kind: "skill"` is a name that `Query.reloadSkills()` (`d.ts:3202`) lists, asked once by the probe; every other row is a `command`. By the CLI's own model a legacy `.claude/commands/x.md` is a skill. `system/init.skills` is a different, narrower set (it omits `init`, `security-review`, `keybindings-help`); it is a per-turn frame, not available to a catalogue read.
An entry that a host's own `initialize` made (`observe`) has no skill names; it serves models, modes and status, and `commands()` completes it with one probe (kept for 24 h); an entry that already had skills keeps them across `observe`.

**D62. The probe.** `query()` with `createInbox()` and no message, `permissionMode: "default"`, `persistSession: false`, `settings: {disableAllHooks: true}` (a project `SessionStart` hook otherwise runs for a probe: seen with the real CLI; the real test fails without it), and `CLAUDE_CODE_STARTUP_FAILURE_RESULTS=1` so a known refusal arrives as a `result` frame with `startup_failure_reason` (without the variable the CLI writes stderr only; `ORG_*` reasons arrive either way). The probe iterates the stream (to catch that frame), races `initializationResult()` against a 20 s clock timer (no control request has a timeout) and then `reloadSkills()` against the same timer (a CLI that cannot list skills, or is slow to, still gives its models and commands), and closes the query and ends the inbox in `finally`. No `canUseTool` or `onElicitation`: nothing is ever sent, so nothing can ask. With no cwd named the probe runs in `stateDir` (created if missing), never the user's home, whose `.claude` the CLI would read as a project's. MCP servers of the project still start for a probe, as for any host. Concurrent requests for one cwd share one probe; a probe that was running when `invalidate` was called is returned but not cached (generation counter).

**D63. The cache.** Memory plus `<stateDir>/catalog.json` (`0600`, atomic rename, `version: 1`, the binary's path: another binary discards the file), per cwd, 24 h, 32 cwds (oldest out), every call serialised. A persisted `initialize` answer is re-validated by a zod schema of exactly the typed fields on read, so the cached value is a real `SDKControlInitializeResponse`; one bad entry loses only itself. The file holds the account (`email`, `organization`) as the CLI answered it. A directory that cannot be written leaves a memory cache.

**D64. Status.** Cases: binary missing (`cli.found === false`: no process; installed false); refused (a startup reason, told in the phone's words from a table keyed by the reason; `ORG_POLICY_LIMIT_PREFIXES` text passed through; any other failure: "could not start: …" with the SDK's clipped message), installed, not usable; signed out; version mismatch; ok. Signed out is `account.apiProvider === "firstParty"` with no `email`, `subscriptionType`, `tokenSource` other than `"none"`, or `apiKeySource` other than `"none"`: the real answer of a CLI with no key and an empty home is `{tokenSource: "none", apiProvider: "firstParty"}`; any other provider authenticates outside Claude Code, so its auth is `unknown` and it is usable. A version mismatch (`claude_code_version` vs `services.expectedCliVersion`) is a warning and usable. A status reuses the newest answer (a probe's or a host's `observe`) up to 60 s old, else probes once (shared with catalogue reads). It does not emit `status_changed`; the app reads `status()` when it needs it.

**D65. Modes.** One axis `permissions`, six options in D12's order, `auto` only if some listed model has `supportsAutoMode` (the axis is the backend's, the flag a model's), default `default`; `bypassPermissions` says "Warning: …" (OQ8). Descriptions follow the SDK's `PermissionMode` doc (`d.ts:2569`). All six work through `setPermissionMode` against the real CLI offline, from a session started in `default` and in `bypassPermissions` (with `allowDangerouslySkipPermissions: true`): checked by `reinitialize().current_permission_mode` in a scratch run (not kept as a test: it is lane D's behaviour).

**D66. Failures are values.** A read whose data does not match the SDK's types (a command without `description`) is a `backend_error` rejection, never a throw. A probe failure is a `backend_error`, or `auth` for a refusal a sign-in fixes; it is not cached.

## Facts that differ from the plan or the research

- `system/init` is **not** emitted before a turn (a probe sees no frames), so `terminal_slash_commands` and `skills` of the frame cannot feed a catalogue read (research 05 §7 assumes they can).
- `initialize.commands` rows are `{name, description, argumentHint, aliases?, builtin?}` plus an untyped `plugin`; nothing marks a skill. Bundled skills carry `builtin: true`.
- A probe runs `SessionStart` hooks of the project unless `disableAllHooks` is passed (not in research 01 §6).
- `startup_failure_reason` reaches a host only as a `result` frame, and only with `CLAUDE_CODE_STARTUP_FAILURE_RESULTS` for most reasons (binary `mEe`/`c`); `initializationResult()` then rejects with `errorClass: "error_result"` whose message is the frame's text. Spawn failures (`executable_not_found`, `executable_launch_failed`) carry no frame; the CLI's own "exists but failed to launch" text is misleading for a missing cwd.
- The SDK's session-less `Query` answers `reloadSkills()` and `getContextUsage()` with the same skill set, which differs from `init.skills`.

## For other lanes

- **D (live):** `setModel` validates through `catalogue.model(cwd, id)` (undefined → `not_found`); keep the requested id for `model_changed` and use `listedModelId` only for a model the CLI chose; rule 21 opens in the *last* mode (`bypassPermissions`) and sets every listed one, so `allowDangerouslySkipPermissions: true` is needed; answer a built-in that never reaches the model `handled` (rule 13 skips non-`started` dispositions but fails on a rejection); a `skill` command is sent as `/<id> args` like any other.
- **F (ops):** `refresh_models` → `catalogue.invalidate()` (no cwd also forgets the status answer); the account for `settings_overview` is `catalogue.initialize(cwd)`.
- **Integration:** `expectedCliVersion` must be passed by the server layer (D3); `stateDir` must exist or be creatable (`~/.broski/claude-code`). `format_file` in this environment formats at 80 columns, not the repo's 120: use `bunx biome format --write`.
- **Unverified:** a probe that is refused with `ORG_POLICY_LIMIT_PREFIXES` text (`d.ts:2541`, exported by `sdk.mjs`): no offline run produces it, so only the unit test (a failing probe whose message carries the sentence) covers it. The cache is not dropped when the account changes; `invalidate()` (the `refresh_models` op) does it.
- **Deferred:** a `TerminalCommands` hand-off from the host's `init` frame (a port change) would replace the fixed set; a probe limiter (two at once) if many cwds are ever probed together.
