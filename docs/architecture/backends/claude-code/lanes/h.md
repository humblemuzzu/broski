# Lane H · App — decisions (D110–D119)

> Merged in Step 5 (`cc/integrate`). This file is the lane's record as delivered; where the adapter [README](../README.md)'s integration decisions D120–D129 changed something here, the README wins.

Everything is under `lib/screens/agent/` and `test/agent/`; the bridge, the generated contract and the old screens are untouched. Contract facts were read from the zod schemas (`action-list.ts`, `editable-file.ts`, `config-ops.ts`, `custom-tool-ops.ts`, `interactions.ts`, `interaction-replies.ts`, `answer-check.ts`, `extensions.ts`) and checked a second time against the generated Dart (`lib/contract/generated/`: field names, nullability, enums, `contractMaxTextChars` = 1,048,576 = `MAX_TEXT_CHARS`).

**D110. A file opens beside its list, inside the same result sheet.** `ResultActions` gained `attempt`: it calls the backend and hands back the `Outcome` without replacing the result the host shows (`call` still replaces it and tells a refusal above the view). `FileDrillDown` (`panels/file_drill_down.dart`) holds the list result, opens a file with `attempt`, shows `EditableFileView` in its place with a *Files* back button, and on the way back reads the list again (so a saved, created or deleted file shows) with the list's own read call. `ConfigFilesView` and `CustomToolsView` are presentational and use it. Evidence: `editable_file_test.dart` "a file opens with a way back…", "going back with unsaved text asks first".

**D111. Every refusal the contract names for a file is its own case** (`panels/file_verdict.dart`): `stale`, `invalid_input`, `unsupported`, `not_found`, anything else / unreached. A refusal never discards the text. `stale` offers one explicit button, *Discard my edit and reload*, which reads the file (no `change`); nothing sends a write on its own, and a second save is at the revision of the last answer. A write that succeeds replaces the shown file with the answer's (new revision, new `file.id` for a created file). Delete is shown for an `exists && editable` file, asks first, and on success goes back to the list. Save/Create/Delete/Back sit above the text so they stay reachable in a half-height sheet. The text is bounded by `contractMaxTextChars`: over it Save is disabled and says by how much (nothing is cut). Read-only: `!editable` shows a *read-only* pill; `truncated` shows why (a write would replace the whole file with the part shown). `problems[]` are listed above the text.

**D112. Custom tools are edited from the list.** A `custom_tools` row opens `custom_tool` with the row's id as `toolId` (the contract documents that id), *New tool* opens `custom_tool` with no id (the template, `exists` false, Create writes at the template revision), and the row's own actions (test, delete) are the list's. A test's output is the list's `note`, shown in a selectable code box. `customToolPanel` moved from `OpPlace.backend` to `OpPlace.unlisted`: the list is the one entry, as `config_file` is opened from `config_files`.

**D113. Plan approval picks the next mode.** `PlanView` shows `PlanModePicker` (choice chips, the option's description under the chosen one) when the request has `modeOptions` and the decision is *Approve*. It starts on `defaultValue` when that is one of the options, else on nothing (the reply then carries no `modeAfter` and the backend takes its own). The reply goes through the existing `planDraft(modeAfter:)` and the Dart `answerProblem`, which already refuses a mode not offered or sent with a rejection. No picker for a request without `modeOptions`.

**D114. The prompt suggestion is the composer's chip** (`composer/prompt_suggestion_chip.dart`), no longer a line in `NoticesStrip`. It shows the newest `prompt_suggestion` while the composer is empty and no run is on; a tap writes the text into the composer and sends nothing. A run starting marks the suggestion in hand as spent (by identity, so a newer one with the same text is still shown); one that arrives during a run is offered when the run has ended.

**D115. Project operations from the Projects tab: the generic half is built, the wiring is Step 7's.** `projectPanels(backend)` and `showProjectPanels(context, backend, cwd:, name:)` (`panels/panels_sheet.dart`) open the `OpPlace.project` panels on a directory with an empty-id `SessionRef`; the config panels already take only `cwd` (`plugins` takes an optional session). The Projects tab is the old `projects_screen.dart`, and its long-press menu is `lib/screens/dialogs/project_context_menu.dart`, both outside lane H's boundary (old Claude Code screens). Step 7 wires it: in that menu, for a `ContractSelection`, add a tile per `projectPanels(descriptor)` that closes the menu and calls `showProjectPanels(context, descriptor, cwd: project.path, name: project.name)` (the descriptor comes from `backendsProvider`, as `openContractProject` reads it). Proven by `project_panels_test.dart`.

**D116. Session list parity (PLAN §10 row 1).** What the generic list already had: paging, pull-to-refresh, archive toggle, row actions, the saved copy offline, a directory on a *new session*. The contract's list query is `{cwd?, archived, parent?}` and the order is fixed (newest updated first), so the rest is app-side on the rows read: **added** to every list (`SessionListView(tools: true)`, off for the children screen): search (every word in title, directory or source, any case), order (bridge order / newest created / title), one-directory filter (when more than one directory is in view), group by directory (header with name, path and count); the list says how many rows the search looked through while more pages exist. **Not added: the title exclude filters** (hide titles matching a substring or `/regex/`): the old ones persist in the old `sessionsTitleExcludeFilters` provider and storage, which `lib/agent` may not import (rule 2); an in-memory version would be forgotten at every restart, which is not what the old screen gave. They belong with a storage-backed, per-machine preference in the selection layer outside `lib/agent`, read by `SessionListView` through a small provider the screen passes in; that is Step 7. The old **diff-stat badges** are dropped in PLAN §10.

**D117. Groups are by name, in first-appearance order** (`panels/grouping.dart`), for action lists and config files: a row joins the section of its `group` wherever it sits, instead of starting a new header at every change. Rows with no group form one untitled section.

**D118. Status tone → colour comes only from the theme's semantic tokens** (`neutral` → `textMuted`, `ok` → `success`, `busy` → `info`, `warning` → `warning`, `error` → `error`); the label is shown as the backend worded it.
