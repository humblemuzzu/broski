# Lane B · Mapping (D50–D59)

`packages/bridge/src/backends/claude-code/mapping/` (pure: no I/O, no SDK at run time, nothing throws). Tests: `packages/bridge/src/__tests__/claude-code/mapping/` (11 files, 272 tests, ~0.4 s, no CLI process). Entry point `CLAUDE_CODE_MAPPING = {createMapper, turnOutcome}` is unchanged; `createFrameMapper(seed, now = Date.now)` takes an optional clock (a compatible extra parameter, not a port change) for `retry_scheduled.retryAt`.

`SDKMessage` is mapped by `mapper.ts` (a `switch` the type check keeps exhaustive) and documented, kind by kind, in `frame-kinds.ts` (`FRAME_KINDS: Record<FrameKey, shows | ignored>`, typed over the union: an SDK that adds a variant fails the type check there). 42 kinds = the 39 variants with `result` in 5 subtypes and `system` in 28. Frames `sdk.mjs` passes through that the types do not declare are listed in `UNDECLARED_FRAMES` and ignored.

## Decisions

**D50. A subagent's work is in its own stream, and nested in the parent's while the parent's call runs.** Every event of a subagent frame goes to the child stream (`MappedEvent.agentId`, no `parentToolCallId`) when the frame's `agent_id` is a valid child ref (`ids.ts childRef`); and to every stream the call that runs the subagent (`parent_tool_use_id`) is shown in, nested with `parentToolCallId`, **only while that call is open**. A frame with only `parent_tool_use_id` is nested in the parent's streams alone; a frame that fits neither is dropped. Why, from the contract's rules: `tool_started.parentToolCallId` must name a tool that is *running* in that stream (`testing/stream-rules.ts` `toolProblems`) and a block's parent must be a tool of the run (`blockProblems`), so a background agent (`Agent` returns `async_launched` at once; `fixture:subagent-background` shows the agent's text 14 frames after the call ended) cannot be nested and goes to the child stream only; a foreground agent (`fixture:subagent`: its frames sit between `task_started` and the call's result) is nested, because the app draws nested work from `parentToolCallId` (`lib/agent/ui/chat/tool_card.dart` `_nestedView`) and STEP-3 §8 join 3 asks for both views. A subagent inside a subagent follows the same rule: its streams are its own plus the streams its call is shown in. Tests: `retraction_subagents.test.ts`, `fixture_events.test.ts`.

**D51. A tool call starts at its `assistant` frame, not at `content_block_start`.** The frame holds the whole input, so `tool_started` carries `input` and `title`; `input_json_delta` says nothing (no half-JSON, the old mapper's defect). `ToolUpdate` has no title, so a card started at `content_block_start` would never get one (`tool_card.dart` shows `title ?? name`), and history (lane A, `toolTitle`) would read differently from live. Cost: a card appears when its input has finished streaming, not while it streams.

**D52. Blocks: `<message.id>:<index>`, finished by the first of the assistant frame (authoritative text), `content_block_stop`, `message_stop`.** The assistant frame of a streamed block takes the index of the streamed block it completes (a `tool_use` by its id, text/thinking the lowest unclaimed of its type: `message-ledger.ts`); a message nobody streamed (a subagent's, a synthetic one) numbers its frames in arrival order, which is how history numbers the entries of one `message.id`. A block that already finished adds nothing in either order (no duplicate text, no reused block id); a resent frame (same uuid) adds nothing. Deltas are cut to what the block can still hold so they always add up to `block_finished.text` (the stream rules compare them). A block the stream announced but no frame shows (redacted thinking) still takes its index.

**D53. Tool outcomes come from the CLI's wording, and a person's denial reads as `denied` only when it starts like the CLI's.** `tool_result.is_error` is all the block says. `tool-outcome.ts` reads the text: "…this call was stopped while running" or "[Request interrupted by user" → `aborted` (no error text shown: it is prose for the model); "The user doesn't want to …", "Permission to use …", "Permission for this …" → `denied`; anything else `failed`. A `system/permission_denied` frame marks its call, whose failed result is then `denied`. The CLI hands a `canUseTool` deny's `message` back verbatim as the result (`fixture:permission-deny`: "Not that file."), so **a human denial reads as `failed` unless lane E's message begins with `HUMAN_DENIAL_PREFIX`** (exported from `mapping/tool-outcome.ts`, = the CLI's own opening, "The user doesn't want to "). Integration decides E's wording. `tool_result_meta[].non_execution_kind` / `permission_decision` would say it exactly (binary: "@internal Display metadata… user-rejected / permission-rule / automode-* / interrupted / cancelled"), but it is not in `sdk.d.ts` and history (lane A) cannot see it, so live and history would disagree; it is deliberately not read.

**D54. Compaction.** `status: compacting` → `compaction_started`; `status: null` + `compact_result: failed` → `compaction_finished{failed, compact_error}`; `+ success` waits for `compact_boundary` → `completed{tokensBefore: pre_tokens, tokensAfter: post_tokens}` (Q13: the boundary comes after `init`). A boundary nobody announced is a started+finished pair with its own trigger; one the boundary never closed ends `completed` at the turn's `result` (`aborted` if the turn was). The trigger is inferred (`status` does not say): a compaction that starts before the turn's `init`/first request is `manual`, one inside a turn `auto` (`fixture:compaction` shows `compacting` before `init`). **The `auto` case is unverified: no recording, and the test bed could not make the CLI auto-compact offline** (`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` + `CLAUDE_CODE_AUTO_COMPACT_WINDOW` did not trigger it with the scripted 100-token usage).

**D55. Usage.** `usage_updated` at each `result` from `modelUsage` (summed over models, subagents included) and `total_cost_usd`; results are cumulative per process, so each replaces the last, never summed. A result with an empty `modelUsage` (an abort before any request, a crash) yields nothing instead of zeroing the totals. `contextWindow` is the session model's (`init.model`), else the only model used, else none. `contextTokens` is read from the last `message` entry of `result.usage.iterations` (BetaUsage docs: "calculate the context window size from the last `message` entry"); **the test bed's results carry `iterations: []`, so this is unverified against a real API.**

**D56. Notices.** `informational` (`warning` → warning, else info), `notification` (`high`/`immediate` → warning), `local_command_output`, `model_refusal_fallback` (its `content`, else "<a> refused the request; continuing with <b>"), `model_refusal_no_fallback` (only when it has words: the refused turn's own error text and outcome say the rest), `mirror_error`, `worker_shutting_down`, `plugin_install` (failed only). A synthetic API-error assistant frame (`error` set) is a `notice{error}` with its text, not a block: it is the CLI speaking, and the run's outcome carries the same message. `result.result` is never shown (the old mapper emitted it as a second copy of the answer).

**D57. `settle(outcome)`** finishes every open block with its text so far, ends every open tool call (`aborted` when the outcome is, else `failed` "The tool call ended without a result"; once per stream it was shown in), ends a retry still scheduled (`retry_finished{false}`) and a compaction under way (`completed`/`aborted`).

**D58. Retry.** `api_retry` → `retry_scheduled{attempt, maxAttempts, retryAt = now + retry_delay_ms, message}` (every attempt announced). The CLI sends no finish frame (Q13), so `retry_finished{true}` comes with the next main-loop frame that proves a request got through (a `stream_event`, an `assistant` without `error`), `{false}` with an `assistant` frame that has `error` (the CLI giving up) or an aborted/errored `result`. `system/status` and tool progress prove nothing; a subagent's frames are not main-loop frames.

**D59. Faults and the unknown.** `map` and `settle` never throw: a fault in the mapping is one `notice{warning}` for the session, then silence. A frame type the SDK adds later is ignored (the `switch` fails the type check at the SDK bump). Every id, index and enum read off a frame is read as data (`wire-id.ts`: a string within `MAX_ID_CHARS`; a small integer index; `RateLimitStatus.safeParse`): the robustness test mutates every field of every recorded and sample frame and asserts no throw and only events `AgentEvent` accepts.

## Contradicts the plan or the research

- **Research 02 §5.1** says an aborted tool is signalled by `aborted: true` on the assistant frame; the frame that carries it is a cut *text* block. A cut tool shows only in its result's text (`fixture:interrupt-mid-tool`).
- **Research 02 §2.2 / §9.1** lists `user` "echoes of host sends": none is recorded (no fixture has one, with or without a uuid), only tool results, the CLI's `[Request interrupted by user…]` text, synthetic compaction/refusal text and `isReplay` command output. `user_message` is therefore emitted only for a prompt the host did not send (subagent prompts go to the child stream).
- **Research 02 §3.3** ("an abort is a success subtype") is wrong, as D31 already says.
- `tool_use_result` of a failed call is a string, not an Output object (research 02 §5.1).
- The checker (`testing/stream-rules.ts`) does not clear open blocks and tools on `messages_retracted`, although the contract says retraction removes them "open or finished" (core README, `session-reducer.ts`). The mapper follows the contract and forgets them; a retraction of an *open* item therefore cannot be proved with `streamViolations` and is tested through `applyEvent` (`retraction_subagents.test.ts`).
- Undeclared but present in 2.1.316 frames: `tool_result_meta`, `tool_use_meta`, `forwardNestedSubagentToolCalls` (an `sdk.mjs` option). None is used.

## What other lanes must know

- **D (host).** The mapper emits no `run_*`, `interaction_*`, `queue_changed`, `model_changed`, `mode_changed`, nor a `user_message` for a send you `noteSend`. Feed it **every** frame of the process in order, `command_lifecycle` and `system/init` included (both are no-ops), and call `settle` before `run_finished`. `init`'s model/mode/catalogue, `commands_changed`, `session_state_changed`, `elicitation_complete` (→ desk) are yours. Events with `agentId` belong to that child's stream; **a child stream needs its own run** around them (the stream rules refuse blocks and tools outside a run). A `session_replaced` means a new mapper for the new session id (child refs embed the session id). `createMapper(seed)` has no clock: `retryAt` uses `Date.now`.
- **A (store).** Use `toolResultOf(block, toolUseResult, {entryUuid, blockIndex}, toolName)`, `fileChangesOf`, `toolTitle`, `imageRefsOf/imageAt` exactly as the live path does. The live image id is `<frame.uuid>:<block>[:<inner>]`. `d.ts:5718` says a multi-block *assistant* message is split into frames with per-block **derived** uuids; whether a user entry with several tool results is split the same way is unverified, and if it is, a live image id will not resolve with `readAttachment` until the run is reread. A user prompt's item id is `userItemId(uuid)`. Block ids are `<message.id>:<n>` with n counted by arrival among the frames of one message.
- **E (asks).** To make a person's denial read as `denied`, begin the deny message with `HUMAN_DENIAL_PREFIX` (D53). `toolTitle`/`fileChangesOf(toolName, input, structured)` are the preview helpers; `fileChangesOf` returns `[]` for any tool but Write, Edit, NotebookEdit.
- **G (terminal).** The tail can feed the same mapper with the frames it can build, or call the shared helpers for entries it translates itself.
- **Integration.** (1) Choose E's deny wording (D53). (2) `contextTokens` and the `auto` compaction trigger are unverified against a real API (D54, D55). (3) The checker gap on retraction (above). (4) `usage_updated` carries no `contextTokens` in the test bed.

## Not done

- No recording exists for: a refusal **with** a fallback (retraction is tested with built frames; the dialog cannot be reached offline, Q13), an auto compaction, a rate limit event, a prompt suggestion, a conversation reset, a nested subagent. Those mappings are tested on frames built from recorded ones (`frames.ts`), not on recordings.
