## Decisions

### D70. The transcript cut is tracked from frames

Every main-thread `user` and `assistant` frame carries the uuid of its chain entry; the prompt's own entry (uuid = the send's) has no frame. Proof against the real CLI: `T/frame_uuids.test.ts` (a tool turn, a thinking turn and an interrupted turn: the chain is exactly `[user:<sent>, …frames]`, the `[Request interrupted by user]` entry included). `T/chain_tail.test.ts` runs a text, a tool, a stopped, a steered and a compacted run in one session and checks that each run's `LiveRow.cut` equals the chain's end read from disk. So the host reads `store.lastChainUuid` once, when it opens an existing session, and follows the frames after that (`run-tracker.ts` `noteEntry`; frames with `parent_tool_use_id` or `agent_id` are a subagent's and are skipped, `frame-handler.ts` `entry`). `null` after a `/clear` (D77); `undefined` (no cut) when the store could not tell.

### D71. A run starts when a send is dispatched or on `running`, and ends on `idle`

`run_started` comes from `PromptDesk.begin` (trigger `prompt`, or `queue` for the head of the queue) and from a `session_state_changed{running}` with no run (trigger `system`). **Nothing else starts a run**: not `init`, not a stream frame, not a `user` frame. A run that starts and never gets its `idle` would block every prompt (`busy`) and could not be stopped, and every one of the 21 recorded scenarios begins with `running` (`T/fixture_replay.test.ts` replays them all). `run_finished` comes from `idle` (`frame-handler.ts` `state` → `run-end.ts`), with three exceptions that are the CLI being gone or not owing an `idle`: the process ends (D74's kill included), and a Stop cancelled the run's only send before the CLI began it (`lifecycle cancelled` while `aborting` and not `started`; `host.ts` `cancelledBeforeStart`, one macrotask later and only if still not started). No `queued_turn_count` fallback. The order at the end of a run is fixed by the stream rules: the mapper's `settle`, the child feeds, `desk.withdrawRun`, a still-open compaction or retry, `run_finished`, then the catalogue row (`store.invalidate`, `store.announce`), then the queue (D73). Every step before `run_finished` is guarded (`attempt.ts`): a part of another lane that throws becomes a notice and the run still finishes (`T/frames.test.ts`).

### D72. A steer is a queue item until the CLI starts it

`steer` with a run active pushes the message at once with `priority: "next"` and lists it in `queue_changed` with `delivery: "steer"`; it leaves the queue and is shown as the `user_message` when `command_lifecycle` says `started` (or `completed`) for its uuid. A start-mode send is shown at dispatch, right after `run_started`. `cancelQueued` of a steer answers `stale` (it is the CLI's). When the CLI cancels a steer without a Stop (`lifecycle cancelled`), its text goes back in `input_returned` at once. A steer the CLI has not reported by the end of the run stays queued (a steer that arrives just after the turn ended runs as the next turn, and showing it back to the person as well would duplicate it); a Stop with no run gives such leftovers back, and so does the end of the process. Evidence: `T/steer_queue.test.ts`, `T/frames.test.ts`, `T/stop_fake.test.ts`; the CLI side is `fixture:steer-next` (`lc:queued … lc:started`) and 08-spike Q3/Q4.

### D73. The queue is the adapter's, one item per run

`queue` with a run active holds the input (`queue_changed`, `delivery: "queue"`, cancellable, bounded by `MAX_LIST_ITEMS`); when the run settles and was not stopped, the oldest item is pushed as a new run (trigger `queue`, its own `user_message`). One at a time, never batched (the CLI batches its own `later` sends into one turn, 08-spike Q4, so an item could not be cancelled once pushed). A run that was stopped returns the whole queue instead (D74).

### D74. Stop

`interruptQuery(query, {cancelQueued: true})` (`d.ts:2952` declares no parameter; `mjs` `async interrupt(e)` takes `cancelQueued`; `d.ts` `SDKControlInterruptRequest.cancel_queued`). Never `perTaskStopAffordance`. After the receipt and one macrotask (the frames that were read before it reach the host), the queue goes back in one `input_returned`, steering first. Three things the real CLI forced:

- **The CLI answers nothing → the process is closed after 5 s** (`INTERRUPT_DEADLINE_MS`), and the run ends `aborted` with it ("Stop means stop"; `T/stop_fake.test.ts`, with a real wait).
- **A Stop can reach the CLI ahead of the message it was meant for.** 08-spike Q3 never exercised this. With the spike rig: interrupt 0 ms after the send gives the receipt `{still_queued: [], cancelled: []}` and the turn then runs as if nothing had happened; at 50 ms the receipt lists the send as cancelled and the CLI emits `running, lc:queued, lc:cancelled, idle` (no `init`, no request); from 150 ms on it is the normal abort. So when the turn begins (`running`, `lc:started`, `init` or any frame of it) in a run with `aborting` set, the host asks again, once (`frame-handler.ts` `began`, `host.ts` `stopAgain`; `T/stop_fake.test.ts`). The receipt-empty regime is a race the real CLI produces only when the interrupt is written before the message; `T/stop.test.ts` covers the 50 ms regime and mid-request aborts with the real CLI.
- A Stop with a pending ask: the CLI's `signal` aborts the ask (E's desk), and `withdrawRun` runs at the end of the run (`T/asks.test.ts`).

### D75. The outcome of a run

One `result` per turn; the host collects `mapping.turnOutcome(result)` per turn (D31 is B's). The run's outcome: an `aborted` turn wins; then the first turn that did not complete; a run with a Stop asked for and no result at all is `aborted`; a `compact` run with a Stop asked for is `aborted` (below); otherwise `completed` (`run-tracker.ts` `outcomeOf`). A process that ends under a run: `aborted` when a Stop was asked for or the host closed it, else `error{backend_unavailable}` with a notice carrying the SDK's message (the SDK's exit error carries the stderr tail).

### D76. `cancelCompaction` is declared: a Stop of a compaction-only run

`compact` is a `/compact <instructions>` prompt (`prompt-desk.ts` `compaction`, no `user_message`, `ActiveRun.compactOnly`). Interrupting one in real CLI 2.1.316 (probe, now `T/compaction.test.ts`): `status{compacting}`, then `status{null, compact_result: "failed", compact_error: "API Error: Request was aborted."}`, an `assistant` frame `Compaction canceled.`, and a `result` with `subtype: success`, no `terminal_reason`, `num_turns: 0`; the session goes on normally afterwards. So the host (a) makes a stopped compact-only run `aborted` whatever the result says, and (b) turns a `compaction_finished{failed}` that arrives while a Stop is asked for into `{aborted}` (`mapped-routing.ts` `asStopped`), so B may map `compact_result: failed` as `failed` and rule 29 still sees `aborted`. `cancelCompaction` is accepted with no effect and no event when no compaction is under way; a compaction the CLI starts inside a normal run (auto) is refused `unsupported` ("stop the run"), since it cannot be ended alone. `cancelRetry` is not declared (Q13).

### D77. `/clear` replaces the session

`conversation_reset` (`d.ts:5391`, emitted by `/clear`, plan-mode exit with clear, fresh session) arrives inside the run that asked for it, with the CLI's new session id. The host keeps its process, emits `session_replaced` with the new ref, re-keys itself in the registry (`hooks.renamed`), starts a fresh mapper (the old one is settled first), forgets its child feeds, resets the chain to `null` and claims the new id in the journal (`session-reset.ts`). The old session keeps its history and is no longer hosted. Real CLI: `T/clear.test.ts` (the next request carries none of the old history). An id that is not a UUID is refused with a notice. The frame is not passed to the mapper.

### D78. Model, thinking and mode

- `setModel(id)`: `catalogue.model(cwd, id)` (`undefined` → `not_found`, `unavailableReason` → `invalid_input`), then `Query.setModel(id)` (the listed id is `ModelInfo.value`, which `setModel` and `--model` take; `mjs` `set_model`), then `model_changed{modelId, thinking}`. The next request carries it, also mid-run (real CLI: `T/settings.test.ts`, request 2 of a run is `claude-sonnet-5-5` after `setModel` between the tool call and its result). `modelSwitch: next_request` stands.
- `setThinking(value)`: the value must be in the current model's `ThinkingSpec` and an `EffortLevel`; `applyFlagSettings({effortLevel})` (`mjs` `apply_flag_settings`); the request then carries `output_config.effort`. `model_changed` replaces both fields, so every emission carries the current model and thinking.
- `setMode`: `PERMISSIONS_AXIS` only; the value must be offered by `catalogue.modes(cwd)` (every `PermissionMode` when the catalogue cannot say); `Query.setPermissionMode`; `mode_changed` is emitted even for an unchanged value (an explicit set is an event). All six modes work with the real CLI, `bypassPermissions` included (`allowDangerouslySkipPermissions`).
- What the CLI reports: `init.permissionMode` and `status.permissionMode` become `mode_changed` when they differ (plan approval's `setMode` update arrives this way). `init.model` is a wire id: it becomes a `model_changed` through `catalogue.listedModelId` only when it differs from the last wire seen and the model was **not** chosen here since (two listed ids can resolve to one wire id, e.g. `default` and `opus` → `claude-opus-5-5`, and a report must not undo the choice; `T/frames.test.ts`). `Options.model` and `Options.effort` are passed only when a person named them (new session options, `setModel`, `setThinking`), never from what the CLI reported; an existing session starts on the CLI's own default. `init` carries no `effort` in this setup, so the thinking shown is only what was set.
- A new session opens in the mode asked for (default `default`, always passed, PLAN fact 5), with the default listed model shown (`catalogue.models`) and the options validated before any process starts.

### D79. Smaller choices

- **Prompt suggestions** (`Options.promptSuggestions`, `d.ts:2133`) cost a request per turn and are not in D5; they are on only when the user's effective settings say `promptSuggestionEnabled === true` (`host-launch.ts`). Lane F's `session_settings` toggle must write `true` explicitly and show an absent key as off, or the extension never fires.
- **A restarted process resumes** when the CLI wrote the session (an `init` was seen) or the file is found by `store.locate`; otherwise it creates it again with the same `sessionId`. Prompts, `setModel`, `setThinking` and `setMode` on a host whose process ended start a new one first, with the session's mode, model and thinking as they stand.
- **One prompt, one validation order**: closed, UUID, the input itself (a `file` attachment is `unsupported`, an image type the API does not read is `invalid_input`, empty is `invalid_input`), busy, only then a process is started. Nothing is dropped.
- **Mentions**: a file is `@<path>` (`@"<path>"` when it has whitespace; the quoted form attaches the file with the real CLI, `T/input.test.ts`), an agent `@agent-<name>`, a command `/<id> <args>`; text first, then the mentions on a new line; images follow as base64 blocks, so the first image of a prompt with text is block 1 and the live `ImageRef` ids (`<uuid>:1`) match the stored entry (`T/input.test.ts` reads the transcript back). The CLI keeps a sent image in its own temp dir (`CLAUDE_CODE_TMPDIR`), not in the repo.
- **Idle grace**: a host nobody views, with no run, ask, compaction, retry or queued input, ends 30 s later (`idle-watch.ts`, the injected `Clock`); attaching or any new work cancels it. A pending ask keeps its host open indefinitely (`T/asks.test.ts`).
- **`withHost` for a session nobody hosts** starts a transient process (a resume with an empty inbox), registers it for `dispose`, closes it in `finally`; `unsupported` for a session a terminal writes and for a child ref, `not_found` for ids that are not sessions. `withLiveHost` hands `undefined` to `work` while a host has no process. A `work` that throws comes back as `backend_error` (both calls), so an op's bug is a rejection and not a thrown error out of the adapter.
- **The model of a session that exists** is the store's `summary.modelId`, mapped through `catalogue.listedModelId` when it is a wire id; when the current model is not a listed one, a thinking level is checked against the default model's.
- **Child feeds** (`child-router.ts`): events with `MappedEvent.agentId` go to a per-agent feed with its own `run_started{system}`, which ends with its `task_notification` or with the parent's run; `openChild` follows a hosted parent live and opens a static empty session otherwise (`store.get` decides `not_found`). At most 256 feeds per host.

## Facts that contradict the plan, the research or the driver

1. **`conformance/delivered.ts` reads the wrong message for the first request of a session.** CLI 2.1.316 sends `messages: [user, system]` on the first request (an `# Environment` message with role `system` follows the first user message) and `[user, system(str), assistant, user]` on the second, so `body.messages.at(-1)` is the environment message and rule 13 sees no attachment, mention or command. With the `system` messages filtered out the driver's parsing of image, `@path`, `@agent-…` and `<command-name>` matches what lane D sends (`T/input.test.ts`, "what the conformance driver reads back"). The driver should take the last message whose role is `user`.
2. **Rule 15's second half races the CLI's start.** `holding()` waits for `run_started` (the adapter's, at dispatch), then the rule aborts; the first prompt of a fresh session needs ~110 ms of CLI start before its request exists, so the abort usually cancels the message before it reaches the endpoint, the `hold` step stays in the session's script, and the retried prompt consumes it and waits on a gate nobody releases (traced: `s4 run_finished{aborted}`, `run_started`, `user_message`, then 15 s of nothing). The adapter is right (Stop cancels a send the CLI has not begun); the driver should replace a session's unconsumed steps on `arrange` or wait until the router has seen the request.
3. Research 01 §3.3 and 08-spike Q3 give no case for a Stop that arrives before its message (D74). Research 02 §3.3's rule for compaction does not cover the interrupted `/compact` (D76).
4. `system/init` repeats per turn and has no `effort`; PLAN fact 6's "first frame of a turn" is, for starting a run, `running` only (D71).

## What other lanes must know

- **B (mapping)**: the host swallows `conversation_reset`, `command_lifecycle` and `session_state_changed` (never passed to `map`); every other frame is. The host emits `run_*`, the user message of a noted send (at dispatch or when the CLI starts a steer), `queue_changed`, `input_returned`, `model_changed`, `mode_changed`, `session_replaced`. `settle(outcome)` is called with `aborted` when the run's outcome is, once per run end and once per `/clear`. A `compaction_finished{failed}` while a Stop is asked for is shown as `aborted` by the host. `turnOutcome` for the interrupted `/compact` (success, no `terminal_reason`) is `completed`; the host overrides it for a stopped compact-only run.
- **E (asks)**: `AskHost.activeRunId()` is the host's run (defined from dispatch, so an ask raised before the CLI's first frame still blocks it); `withdrawRun(runId)` runs before every `run_finished`, `expireAll()` when the process ends and when the host finishes; `elicitationComplete(id)` on `system/elicitation_complete`; `abortRun()` is the host's Stop and does not wait for the run to end; `planModeOptions()` is the permissions axis from `catalogue.modes(cwd)` without `plan`, loaded when the host starts (undefined until then). `T/helpers/human-desk.ts` is a test double with the waiting semantics, not E's.
- **A (store)**: `lastChainUuid(id)` is read once per `open(existing)`, `locate` also when a restarted process decides between `resume` and `sessionId`; `invalidate(id)` then `announce(id, live)` run when a run starts and when it ends (fire and forget; `announce` before the file exists emits nothing); `get(childRef)` decides whether a child can be opened; `LiveRow.cut` is present exactly while a run is active; `ownership.notePrompt` is called before the message is pushed and not awaited.
- **C (catalogue)**: `model(cwd, id)` and `modes(cwd)` are called on the control path (a rejected answer from either is passed on, except in `open` of a new session where a failed `models`/`modes` listing without a named model or thinking is not fatal); `observe(cwd, init)` on every host's and transient host's `initialize`; `invalidate(cwd)` on `commands_changed`; `listedModelId(cwd, wire)` on a turn's `init.model`.
- **F (ops)**: `HostView.query` is the live process's `Query`; never iterate, close or interrupt it. `tasks()` follows `background_tasks_changed` (REPLACE) with the statuses of `task_updated`, ambient tasks left out, finished ones removed. `busy()` is "a run, an ask, a compaction, a retry or queued input". `withLiveHost` gives `undefined` for a host whose process ended; `withHost` restarts it.
- **Integration**: the two driver facts above; `prompt_suggestion` needs F's setting (D79); `HostControl` has `cancelCompaction`, so `SessionCapabilities.cancelCompaction` is true (rule 29 will run; a Stop of a compaction was shown to work with a slow summary and with a side request held at the endpoint that is never released, `T/compaction.test.ts`).
