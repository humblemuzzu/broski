## 2. The shape

```
backend.ts ── reads ──────▶ store/ (SessionStore, ports.ts) ◀── LiveOverlay ── live/
     │                                                                          ▲
     ├── open/rename/delete ─▶ live/session-hosts.ts ─ one SessionHost per hosted session
     │                           │  SessionLocks (D2) · LiveState (snapshot + sink) · RunTracker
     │                           │  EventBridge ─▶ mapping/ (B) · PromptDesk · QueueMirror · SessionSettings
     │                           └─ InteractionDesk + RemoteUiContext + permission gate (ui/, E)
     ├── listModels ─▶ models/catalogue.ts (C) ─▶ models/model-runtime.ts (C) ─▶ the one ModelRuntime (services.ts)
     ├── listCommands ─▶ commands.ts (C)   listModes ─▶ modes.ts   status ─▶ status.ts (C)
     └── call(navigate_tree) ─▶ ops/navigate-tree.ts (E) ─ HostAccess ─▶ live/
```

Every event any part emits goes through the session's `LiveState.emit`, which applies `applyEvent` and forwards to the attached sink (README §5 rules 1, 2). Catalog news goes through the one `CatalogFeed`, silenced at `dispose` (rule 4).

### 3.1 Ids (`ids.ts`, README §4)

| Id | Scheme | Why |
|---|---|---|
| `RunId`, `InteractionId`, `QueueItemId`, assistant `MessageId` | `mintRunId()` etc.: `crypto.randomUUID()` | never reused in a session (stream rule 2); Pi has no ids for these (pi §13) |
| `BlockId` (live) | `blockId(messageId, contentIndex)` = `${messageId}:${contentIndex}` | Pi keys blocks by `contentIndex` (report 03 §7.2); `message_update.message` is a *shallow* copy per event whose `content` array is the provider's live partial (PA `src/agent-loop.ts:442-449`), so read it synchronously in the listener and never keep it |
| `ToolCallId` (live) | `new ToolCallIds()` per run; `nextResponse()` at every assistant `message_start` empties it; `liveId(piId)` mints a UUID on first sight, `find(piId)` looks one up; `deny(piId)`/`wasDenied(piId)` record the gate's blocks | A provider's id is at best unique within one response: OpenAI-compatible servers may send none (`id: toolCall.id \|\| ""`, AI `src/api/openai-completions.ts:515`), Gemini's are de-duplicated inside one message only (AI `src/api/google-generative-ai.ts:195-201`); a nested call's is `<parent>/<n>` (PM `src/core/extensions/types.ts:1193-1203`). Every call of a response finishes before the next request (PA `src/agent-loop.ts:540-594`), so the table never needs an older response's ids. Two calls with one id *inside* one response cannot be told apart from `tool_execution_*` events (Pi pairs results the same way); that case stays broken in Pi too |
| `user_message.messageId` (live) and every transcript item id | `entryItemId(entryId, index)` = `${entryId}:${index}`; `index` is `0` for an entry that yields one item, the `contentIndex` for an assistant message's blocks and tool calls | a prompt's live and transcript ids are then equal; parsed back by `parseEntryPart` (last `:`, digits only) |
| `AttachmentId` | `entryAttachmentId(entryId, contentIndex)`: the image block of a persisted user message or tool result | `readAttachment` reads that block from the file (report 02 §11.3) |
| `ToolCallId` (transcript) | `storedToolCallId(assistantEntryId, contentIndex)` = `entryItemId(…)`: where the call sits | contract README §4 makes a `ToolCallId` unique per session; Pi's stored id is the provider's (above: may be empty, repeat across responses, or exceed 256 characters, e.g. `{call_id}\|{item_id}` ids of 400+ characters, AI `src/api/openai-completions.ts:1208-1220`). A `toolResult` entry gets the id of the call it answers from lane A (`EntryContext.toolCallId`, §6 A) |
| entry ids | `isUsableEntryId(id)`: 1..`MAX_ENTRY_ID_CHARS` (128); Pi mints 8 hex or a UUID (PM `src/core/session-manager.ts:277`) | an entry with another id is not Pi's: lane A skips it as unreadable |

**Proven by running** (`sdk_boot.test.ts`): inside a `queueMicrotask` scheduled from the public `message_end` listener of a user message, `sessionManager.getLeafId()` is that message's entry id, and an entry appended there lands right after it in the file. This settles contract README Q28: Pi calls the public listeners and then `appendMessage` in one synchronous stretch (PM `src/core/agent-session.ts:1144-1166`), and the agent loop's own continuation is queued after the listener's microtask, so nothing else is appended between them.

### 3.2 Cursors (`cursor.ts`, README §11.1, report 02 §11.4)

`base64url(JSON {v: 1, k: kind, s: scope, p: position})`, at most `PageCursor`'s 8,192 characters. `scope` is `cursorScope(parts)`, a 43-character SHA-256 digest of what the read pages over, so a long cwd cannot overflow it and a cursor from another read is refused. `decodeCursor` returns `undefined` (the caller answers `invalid_input`) for: a string `PageCursor` refuses, a non-base64url character, bytes that are not JSON, a missing or other `v`, `k` or `s`, a missing `p`, or a `p` the reader's `guard` refuses. The reader's own staleness checks (a keyset row, an anchor item id) come after.

### 3.3 The session lock (D2, refined)

`SessionHosts` owns one `SessionLocks`, keyed by session id. **Held for**: hosting a session (open), a prompt until Pi decides its disposition, `setModel`, `setThinking`, `setMode`, `compact` until Pi has taken it, a hosted rename, a delete, `withIdleSession` (navigate), and ending a host. **Not held for**: `abort`, `answer`, `snapshot`, `close`, reads. Why: a prompt's acceptance can wait on an extension's dialog inside an `input` or `before_agent_start` handler (PM `src/core/agent-session.ts:2117-2126`, `_prepareRun` from `_startRun` `:1873`), and the human's abort and answer must still reach Pi; Pi's `abort()` is safe at any moment (`:2498-2508`), and one requested while a run is being prepared aborts it as soon as it exists (`:1104-1106`, `:1867-1871`). The lock is **not re-entrant**: code that holds it never calls a method that takes it. The lock is in-process only: it orders this bridge's calls, never another `pi` writing the same file (§10 item 4).

### 3.4 The adapter's own session entries (`broski-entries.ts`)

All three are `custom` entries (`SessionManager.appendCustomEntry`, PM `src/core/session-manager.ts:1290`): never in the model's context (`sessionEntryToContextMessages` returns none for them, `:439-465`), hidden in Pi's default tree view (PM `src/modes/interactive/components/tree-selector.ts:359-366`), written to the file only once it holds a user or assistant message (`_persist`, `:1171-1189`).

| Entry | Written by | When | Read by |
|---|---|---|---|
| `broski.origin` | D at session creation; A in every fork it writes | before the first message (flushed with it) | A: `origin: "broski"` (else `"external"`); D: only a `broski` session is hosted with `control` (§10 item 4) |
| `broski.prompt {clientRequestId, imageNames}` | D | in the microtask after a prompt's user message is persisted (§3.1) | A/B: the `user_message` item's `clientRequestId` and image names |
| `broski.permissions {mode}` | D | at every accepted `setMode` and at creation with `ask` | D: the mode a reopened session starts in (§9 item 4) |

## 5. The SDK spike

`src/__tests__/pi/sdk_boot.test.ts` (construction) and `sdk_semantics.test.ts` (behaviour), green under Bun 1.4.4, ~10 ms a test; the factory they share is `helpers/pi-spike.ts`. What worked, exactly:

- **Isolation**: `createPiTestEnv()` (`helpers/pi-test-env.ts`) makes a real-pathed temp root, **removes every environment variable but a short allow-list** (`PATH`, `TMPDIR`, locale, `BUN_*`, `NODE_*`, …), and sets `PI_CODING_AGENT_DIR` (read by `getAgentDir()` on every call, PM `src/config.ts:605-611`), `PI_CODING_AGENT_SESSION_DIR` (read by the CLI, PM `src/main.ts:691-695`; the adapter honours it the same way, lane A) and `HOME` (PM reads `$HOME/.agents/skills` through `process.env.HOME`, PM `src/core/package-manager.ts:233-235, 2464`; pi-ai reads the gcloud ADC file under it, AI `src/env-api-keys.ts:40-71`). `dispose()` restores the whole environment and removes the root. The scrub is not optional: pi-ai signs a provider in from its own environment variables (`DEEPSEEK_API_KEY`, `NVIDIA_API_KEY`, `AWS_PROFILE`, …, AI `src/env-api-keys.ts:73-126`), and on the machine Step 0 was verified on the unscrubbed test env listed `deepseek`, `nvidia`, `opencode` and `opencode-go` models *ahead of* the faux ones, so conformance rule 20 (which runs the first two listed models) would have called real models. `registerFaux` now throws if any non-faux model is available. Explicit options are passed as well: `ModelRuntime.create({authPath, modelsPath})` under the temp agent dir, `SessionManager.create(cwd, sessionDir)`.
- **Faux through the shared runtime**: `fauxProvider({provider, models})` (AI `dist/providers/faux.d.ts`, root export) → `modelRuntime.registerNativeProvider(handle.provider)` (PM `src/core/model-runtime.ts:899-911`) → `await modelRuntime.refresh({allowNetwork: false})`. The faux models are then in `getAvailable()`, stay there across later `refresh()` calls, and `hasConfiguredAuth("faux")` is true. **The scripted OpenAI server is not needed.** Faux facts for the driver: a response step is a message or a (possibly async) factory `(context, options, state, model)` (AI `dist/providers/faux.d.ts`, `FauxResponseFactory`); one step is taken *synchronously* per request (AI `src/providers/faux.ts:524`) and an empty queue answers `stopReason: "error"`, `"No more faux responses queued"` (`:530-540`); a factory that waits must watch `options.signal` itself, because faux checks the signal only while streaming the message it returns (`streamWithDeltas`, `:356-452`).

Asserted: `runtime.services.modelRuntime` and `session.modelRuntime` are the shared instance, and `ModelRuntime.create` (spied) is never called. **The adapter's factory must also pass `settingsManager`** (lane D, project trust): the spike omits it only because its temp project holds nothing trust-gated.
- **Hidden extension**: `{name, hidden: true, factory}` in `extensionFactories` loads; its `tool_call` handler fired for the faux model's `read` call; its `session_start` handler saw `ctx.mode === "rpc"` and `ctx.hasUI === true`.
- **Binding**: `session.bindExtensions({uiContext, mode: "rpc"})` with a full `ExtensionUIContext` whose `theme` is `plainTheme()`.
- **A run**: `session.prompt(text, {preflightResult})` reported `"started"`; the last event was `agent_settled`, exactly once; the faux factory received `options.sessionId === session.sessionId` (so a driver can script per session). Every run also emits and persists a `system`-role message with empty content before the user message (the run's loadout record): `message_start/end` of role `system` are neither a run start nor an item.
- **The file**: `<sessionDir>/<timestamp>_<sessionId>.jsonl` (flat in the given dir), header `{type: "session", version: 3, id, cwd}`. A new session's first entries are `model_change`, `thinking_level_change`, then the `system` message, then the user message.

- **Images**: a one-pixel PNG reached the model and the stored user entry byte for byte (`images.autoResize` left it alone).
- **Extension files**: `<agentDir>/extensions/driver.ts` (plain `export default function (pi) {…}`) loads under Bun with no errors.

**Implements** `createSessionStore(deps): SessionStore` (`ports.ts`), every method:

| Method | Semantics |
|---|---|

## 10. Plan vs contract conflicts

The contract wins (brief §2); each is resolved below as instructed to the lanes.

1. **D17 "clear Pi's queues after an abort" vs README §10 "an abort leaves the queue as the backend leaves it, and `queue_changed` shows the result … Pi keeps steer and follow-up messages".** The contract wins: lane D does **not** call `clearQueue()` on abort (Step 0 had ruled for the plan; its verifier overturned that). What Pi leaves is proven in `sdk_semantics`: an abort during a model request keeps both queues; an abort during a tool still delivers a pending steer into the aborted run at its next turn and keeps a follow-up, which the next run delivers after its own prompt. The terminal's Esc does clear Pi's queue, but it moves the text back into the editor (`restoreQueuedMessagesToEditor`, PM `src/modes/interactive/interactive-mode.ts:4711-4729`); the contract has no "back to the composer", so clearing would lose the user's text. Plan §6 matrix item 1 ("nothing replayed from the queue") is tested as the contract says (§6 F). **Owner**: following the terminal needs a contract change first (README §10's Pi row, and somewhere to hand the text back).
2. **D13 "expiry emits `interaction_resolved{expired}`" vs README §9 table ("resolved: withdrawn … Pi: extension timeout or abort signal"; "expired … Pi: bridge restart").** Lane E reports an extension timeout as `withdrawn`.
3. **D13 "`notify`/`setStatus`/`setWidget`/`setTitle` → `notice`" vs README §15 ("Lost: … fire-and-forget extension UI (`setStatus`, `setWidget`, `setTitle`)").** Only `notify` becomes a notice; `custom()` becomes a notice (README §15).
4. **Plan "Session: `controllable` ✓" vs README §6 ("`controllable` ✗ for terminal sessions (pi §11)") and §17, Not in Phase 1 ("External-session takeover (resuming a terminal-owned CC or Pi session interleaves writers, cc §11, pi §11)").** Pi gives no way to tell that a terminal is driving a session file now (report 01 §12: no lock, no marker), and two writers fork its tree silently (report 02 §8.4). 5. **README §2 rule 3 still names `src/backends/pi-shared/`**; D19/D20 build no `pi-shared/`. Nothing to do now; the contract cleanup that removes `pi-durable` should remove it.

## 12. Open questions and contract gaps

1. **Gap: `DeliveredInput` compares an image's `name`**, which Pi never sends to a model (AI `ImageContent` is `{type, data, mimeType}`). The driver takes the name from the transcript's `ImageRef`, which lane A fills from `broski.prompt.imageNames`; the rule then checks the adapter's record of the name, not the model's input. A contract minor could compare `{mimeType, data}` only.
2. **Gap: a fork point inside an assistant message.** `ForkPoint` names any item; Pi forks at entry boundaries. Lane A refuses an inner point `invalid_input`. The suite forks through the last item only.
3. **Semantics: `navigate_tree` on a `user_message` item** (and on a `notice` item from a `custom_message` entry). The contract says "move the leaf to `itemId`"; Pi moves it to the message's parent and hands back the text to edit (PM `src/core/agent-session.ts:4152-4159`, proven in `sdk_semantics`). Lane E follows Pi (the terminal's `/tree`); the op's description could say so.
4. **Gap: an extension dialog before a run starts** (an `input` or `before_agent_start` handler asking, or a `session_start` handler asking while `open` binds the extensions, §6 D) holds the prompt's acceptance or the open, so the phone's request can reach the core's 120 s deadline; a pre-prompt auto-compaction (`_prepareRun`, PM `src/core/agent-session.ts:1929-1932`) holds a prompt's acceptance the same way, for a model request's length. The contract has no "accepted, waiting" answer.
5. **Settled since Step 0**: compaction forwards the session id when it has one (PM `src/core/compaction/compaction.ts:602-604`; the driver's fallback still covers a request without one); the built-ins load in an SDK host (§6 E). **Still unverified**: `processImage` on a large image (resized bytes are what is stored, so read-back stays exact, but the delivered image differs from the sent one, and `DeliveredInput` compares bytes); Bun's recursive `fs.watch` on Linux (lane A checks first); the extensions' `project_trust` event, which the terminal consults before its trust store (PM `src/core/project-trust.ts:55-70`) and lane D's trust rule (§6 D) does not, because it fires on extensions loaded before trust is known.
6. **The plan's contract gaps** (no tree read, no user `!bash`, no active-tools op) stand; its fourth, "status/widget are notices only", now reads "status and widgets are lost" (§10 item 3).
7. **Risks the lanes cannot remove**: an extension's provider registration is process-wide (§6 C); two calls with one provider tool call id inside one response cannot be told apart (§3.1); an extension or provider that ignores the abort signal holds `abort()` past its deadline and the run open (matrix 7, honestly); a `start` prompt that races an extension's own deferred prompt across Pi's settle window can be refused by Pi (`Agent is already processing`, PM `src/core/agent-session.ts:2137-2142`) and is answered `busy`.
